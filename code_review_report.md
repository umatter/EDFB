# EDFB teaching material: code and didactic review

Date: 2026-09-16. Scope: every notebook under `notebooks/` and `activity/`, the datasets under `data/`, and `README.md`, on commit `a186015`. Method: close reading of every cell of every current notebook (archived R notebooks skimmed), column names checked against the CSV headers, data URLs checked live, and data facts recomputed with plain Python where a finding depends on a number. Nothing was executed end to end: neither the Python stack nor the R packages are installed on this machine, and no notebook in the repository except one carries stored outputs, so the observation "this cell errors" is a reading of the code, verified against the sources for every blocker. Cell numbers are 0-based indices into the notebook JSON.

The report has three layers. Section 1 is the verdict. Sections 2 and 3 are the cross-cutting findings and the course-level didactic assessment, which are the parts worth reading in full. Section 4 gives one page per unit. Section 5 is the action plan. Appendix A holds the complete finding tables (about 170 findings), for use while editing.

## 1. Verdict

The course has the right shape and the wrong state. The arc (linear models, logistic regression, trees and ensembles, clustering, a capstone group project, and a paper-replication activity) is well chosen for a business-school finance audience, the Python and R tracks are genuinely cell-for-cell parallel in units 01 and 02, the banking dataset is a good running example, and several individual design decisions are better than most public teaching material (dropping `duration` as leakage in unit 02, the LPM out-of-range diagnostic, predict-then-observe prompts in the clustering notebook, log returns with a chronological split in the Bitcoin section, a paper-linked 72-row dataset for the Varian activity).

But the material cannot be handed to students in its current form, for three reasons that recur across every unit:

1. **Most notebooks do not run.** Of the twelve student-facing notebooks the README links, six stop with an error or cannot obtain their data on a fresh Colab runtime. Both unit 03 notebooks (relative file path in Python; wrong column names and `yes`/`no` label coding in R), the R unit 02 notebook (two typos), the linked unit 01 solutions notebook (a `SyntaxError` and an `AttributeError`), the Varian starter (a scikit-learn argument removed in 1.6), and 128 of the 141 cells of the main clustering notebook (three CSVs that exist nowhere in the repo or its history). No current notebook has ever been executed and saved with outputs, which is how all of this went unnoticed.

2. **Several headline results are wrong in ways that teach the opposite of the intended lesson.** The Python Bitcoin regression leaks same-period prices into the features and would show students a linear model "predicting" returns with an R² around 0.6. The clustering notebook's central experiment trains cluster-specific credit models on features of one company paired with the default label of another, because of an index-alignment bug. The group project computes an "efficient frontier" from returns it draws from `np.random.normal`, ranks "portfolios" on the outcome they are then evaluated on, and calls a simulated dataset "real". The causal-ML section defines the treatment as the customer's own past response, which no adjustment can turn into an effect of an intervention.

3. **The didactic layer is thinner than the code layer.** No current notebook states learning objectives. Coefficients are never taught before students are asked to interpret them. Accuracy is reported without a base rate on an 89/11 dataset. Class imbalance is handled by undersampling before the split, so every evaluation and the profit exercise run on an artificial class mix. Conclusions are written before the results in the solution notebooks and the causal section. Unit 03 has no exercises, unit 02 and unit 04 have no solutions, and the group project is a fully worked tutorial with an empty "your turn" cell that points to a PDF not in the repo.

None of this is structural. The fixes are mostly local, and the honest versions of the broken lessons (returns are unpredictable; segmentation only helps if segments differ enough; you cannot get a treatment effect without a treatment) are better lessons than the ones currently planted. Section 5 gives an order of work; a focused week would bring the material to a state where every notebook runs and no notebook teaches something false.

## 2. Cross-cutting findings

These are the issues that appear in three or more notebooks. Fixing them once, as a policy, is cheaper than fixing them per notebook.

### 2.1 Nothing has been executed

No current notebook stores outputs (the sole exception, `04_EDFB_Comparison_clustering_methods.ipynb`, stores outputs that contradict its own text in at least three places; see 4.4). Every blocker in this report would have been caught by one "Runtime → Run all" on Colab before commit. The README's reproducibility section promises "Python notebooks pin library versions in the top Setup cell" and "Notes at the top of each notebook indicate the runtime versions they were tested on". Neither statement is true of any current notebook; only the two archived R notebooks carry a "Tested on" line.

**Policy:** before a notebook is linked from the README, run it end to end on a fresh Colab runtime and commit it with outputs (students then see what to expect, and diffs reveal regressions). Add the tested runtime line the README promises, and either pin versions or delete the claim.

### 2.4 Python/R parity is claimed but not delivered

Units 01 and 02 are cell-for-cell mirrors, which is a real asset. But the mirrored cells compute different things:

- R computes R² as squared correlation; Python computes 1 − SSE/SST. Out of sample these differ, and R's version cannot go negative, which hides the Bitcoin lesson.
- Unit 02 Python drops six correlated columns; R drops none and fits a rank-deficient model with an `NA` coefficient no text explains.
- Unit 01 Python plots against `age`; R plots against a 0/1 dummy because the first column differs after encoding.
- Unit 02 Python's `LogisticRegression` is L2-penalised by default; R's `glm` is not. Coefficient tables differ and no note says why.
- Unit 03 Python has no Lasso CV path (fixed `C=1`) while R uses `cv.gamlr`; Python boosting has no early stopping while R does.
- R setup cells install from CRAN source on Colab (15 to 30 minutes before the first useful cell); the archived versions used the Posit binary mirror the README still describes.

**Policy:** parity means same data, same split, same features, same metric definitions, same conclusions. Where the libraries genuinely differ (penalty defaults, `cp` vs `ccp_alpha`, factor vs dummy counting for `mtry`), say so in one sentence rather than pretending equivalence.

### 2.5 Leakage is taught in week 2 and reintroduced in week 3

Unit 02 drops `duration` with the correct reason (call length is known only after the call). Unit 01 uses `duration` as the regression target, which is fine. Unit 03 puts `duration` back in the feature set without comment, where it becomes the root split of the tree and the top of every importance ranking, and then uses it as a covariate in the causal section. The group project predicts same-year revenue growth from same-year revenue. The unit 04 credit models fit clusters and scalers on all rows before splitting. Solutions in unit 01 select lags, thresholds and regularisation strength on the test set, two cells after warning about exactly that.

**Policy:** one decision-time rule, stated once in unit 01 and referred back to in every later unit: "at the moment the decision is made, which columns are known?" Every feature set is checked against it in a markdown line.

### 2.6 Evaluation without a baseline

Accuracy is reported in units 02, 03 and 04 without the majority-class rate (0.887 on the natural data). The Bitcoin "naive baseline" is the lag-1 return, which doubles the error variance and makes a zero-skill model look 30% better than naive. AUC is computed from hard 0/1 predictions instead of probabilities in unit 02 Python and four times in unit 04, so the number in the legend is not the area of the curve drawn. Model comparisons in unit 03 use only accuracy at threshold 0.5.

**Policy:** every metric appears next to the baseline it must beat (majority class, zero forecast, or the global model), and AUC is computed from probabilities.

### 2.7 Pre-written conclusions

Unit 01 solutions ("trading can be profitable", "higher confidence predictions tend to be more accurate"), unit 03 causal section ("individual treatment effects vary significantly, suggesting personalized strategies"), unit 04 ("cluster-specific models often outperform the baseline", asserted three times and never tabulated), the clustering comparison notebook (observations contradicted by the stored figures above them), and the Varian solutions (hard-coded numbers from a 3-fold run while the code does 5-fold, an unfilled `[X]%` placeholder) all contain interpretation written before, or independently of, the result the student will see.

**Policy:** insight cells are written after running, quote the notebook's own numbers, and where the honest result is "no effect" or "the simple model wins", that becomes the lesson.

## 3. Course-level didactic assessment

### 3.1 What a student currently learns

Walking the arc as a student who runs every cell that runs and reads every markdown cell:

- **Unit 01.** They fit a line to synthetic data (good), then a 26-variable model whose R² of 0.01 is printed and never interpreted, see a fake `y = 0.00 * x + 5.12` equation and a zig-zag "fit" plot, check homoscedasticity against row index, and then (Python) watch a linear model predict Bitcoin returns with R² 0.6. They finish believing returns are forecastable.
- **Unit 02.** They see why the LPM fails (well done), fit a logit, and are asked to interpret coefficients that were never explained, on a test set with a 33% positive rate the notebook told them was representative. Their profit calculation is off by roughly a factor of three.
- **Unit 03.** Nothing runs. If it did, all four models would score 0.89 to 0.92 accuracy with no baseline, `duration` would top every ranking, and a causal forest would report a treatment effect of "having said yes last time".
- **Unit 04.** Thirteen cells run, then an upload dialog for a file they do not have. If they had it, the clustering-improves-credit-models conclusion would rest on scrambled labels.
- **Group work.** They run a tutorial, get plots of a random-normal efficient frontier and a cross-sectional "Sharpe ratio", and write a report that ESG predicts growth in "real" data that is simulated.
- **Varian activity.** The starter errors at the first RMSE. The paper is read in class for 30 minutes.

### 3.2 What the arc should teach, and mostly already tries to

The intended progression is sound and the material contains the right moments; they are just not connected:

1. **Fit, evaluate out of sample, and know what "good" means** (unit 01). The synthetic-recovery exercise, the train/test split, RMSE next to the standard deviation of y, and the Bitcoin section's chronological split and log returns are the right ingredients. The missing piece is the honest comparison against a zero forecast, and the sentence "an R² of 0.01 is normal here and the model is still useful for capacity planning".
2. **Probability, threshold, decision, cost** (unit 02). The LPM diagnostic, the comparison table, Exercise 2 (threshold) and Exercise 6 (€5 cost, €100 revenue) form a complete argument ending in the memorable rule "call if p > cost/revenue = 0.05". The notebook has every part and never assembles them.
3. **Flexibility versus variance, and importance versus effect** (unit 03). Tree, forest, boosting on one split with one table is right. What is missing is any observable motivation (a tree overfitting; test AUC versus number of trees) and one paragraph separating "predicts well" from "causes". The causal section should be that paragraph, made concrete, not a tour of five estimators.
4. **Structure without labels, and its limits** (unit 04). Six shapes times four methods with predictions before each run is excellent design. The credit-risk application asks the right question (does segmentation help?) and should answer it with a table, whichever way the answer goes. The valuation application is a credible CFA-style workflow that needs a median, a peer count and a range.
5. **Integrate and defend choices** (group work). Should require a linear baseline (01), a classification variant (02), an ensemble (03), a clustering-based grouping (04), a time-aware evaluation, and a memo that says what simulated data can and cannot show. Currently requires none of these.
6. **Read a paper and reproduce its claim** (Varian). `FLS-data.csv` is the Fernández, Ley and Steel growth dataset Varian uses in his variable-selection comparison, and its column order is the BMA ranking from his table. A lasso path on it, compared with that ranking, is a genuine replication and uses what unit 03 taught. The current OLS-versus-random-forest exercise replicates nothing in the paper.

### 3.3 Misconceptions the material currently plants

Listed because each is the opposite of a lesson the course is meant to deliver:

- Financial returns are predictable with lagged linear models (unit 01 Python leakage; solutions' "profitable strategy" text; lag-1 baseline).
- A test set with an engineered class mix is "representative" (unit 02 undersampling before split).
- Coefficient size is effect size (unit 02 ranking by absolute log-odds; Varian solutions ranking unstandardised OLS coefficients; unit 03 importance read as effect).
- Accuracy near 0.9 is good on a dataset where 0.887 is the majority rate (units 02, 03, 04).
- A causal forest on observational data yields a targeting rule (unit 03 closing recipe).
- Clustering finds "true" groups and silhouette measures correctness (unit 04; silhouette of 0.5 on a visibly wrong split of the moons passes without comment).
- Cluster-specific models beat global models (asserted three times, never shown; and the demonstration is bugged).
- A Sharpe ratio can be computed across firms in one year; an efficient frontier can be fitted to twelve random draws (group work).
- ESG scores predict performance (group work on simulated data described as real).
- Method lists are facts: "random forests handle missing values", "boosting is state of the art" (unit 03 pros/cons, wrong for the implementations used).

### 3.4 Load and pacing

Cell counts per unit: 74, 70, 30, 132 + 141, 31, 19 + 28. Unit 02's preamble is too long; the clustering pair is two to three sessions of material presented as one; unit 03 is too short in prose and too long in package installs (nine heavy R packages for one that is used, one of which is not on CRAN and aborts the loop). Unit 01's nine exercises plus six reflection questions need core/optional marking. The group project is 850 lines of given code and zero lines of student work. Emoji section headings are tolerable for the audience; tick and cross marks as verdicts in summary tables are not, because the figures above them do not support the verdicts.
