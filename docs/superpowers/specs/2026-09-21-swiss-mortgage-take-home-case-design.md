# Take-home case: the mortgage book of a Swiss regional bank — design

**Date:** 2026-09-21
**Status:** approved in conversation, awaiting spec review
**Feeds:** the implementation plan in `docs/superpowers/plans/`

## Purpose

A team take-home notebook for EAIF (AI for Finance), handed out after the class on
linear and logistic regression (SL1, SL2) and before the class on advanced supervised
learning (SL3: LASSO, trees, random forests, gradient boosting, XGBoost, SVM). The first
half repeats linear and logistic regression through worked examples and short exercises;
the second half introduces the SL3 methods hands-on and ends with exercises that use
them. The whole notebook is one business case, in the format business schools teach with:
a fictional Swiss regional bank, a memo from its CRO, and three questions the team
answers in sequence, each with the method that fits it.

Audience: undergraduate business students, working in teams of three to four, about three
hours, discussed in the next class and not graded. Python only; an R mirror may follow.

## The case

**Aare-Säntis Regionalbank AG** (fictional; no real bank, no real households) holds a book
of about 8,000 residential mortgages originated 2019–2022 in seven German-speaking
cantons (ZH, BE, AG, LU, SO, SG, TG). The CRO's memo asks:

- **A1 — Is our collateral valued right?** Build a valuation model for the financed
  properties (linear regression, hedonic pricing).
- **A2 — Which borrowers run into payment trouble, and where do we set the approval
  bar?** Predict trouble within 36 months (logistic regression), choose a threshold from
  the cost of the two errors.
- **B — The risk committee doubts the logit.** Can LASSO, trees, random forests, boosting
  or an SVM do better, and would we dare deploy one of them?

The closing exercises score this year's applications with the chosen model, run an
interest-rate stress through it, and write a five-bullet recommendation to the CRO.

## Data

All data are synthetic and generated by a committed script, so that the non-linearities
that make the advanced methods legitimately beat the logit are planted on purpose, and so
that no licensed Swiss borrower- or property-level data is redistributed.

### Columns of `mortgages.csv`

Property: `canton` (ZH, BE, AG, LU, SO, SG, TG), `property_type` (apartment, house),
`living_area_m2`, `rooms`, `year_built`, `distance_center_km` (to the nearest regional
centre), `energy_label` (A–G), `purchase_price` (CHF).

Borrower: `household_income` (CHF gross per year), `age`, `employment` (employed,
self_employed, retired), `years_client` (years as a client of the bank).

Loan: `loan_amount` (CHF), `rate_type` (fixed, saron), `fixed_years` (0 for saron),
`interest_rate` (percent, the actual rate at origination), `amortisation` (direct,
indirect), `origination_year`.

Derived, provided in the file so the recap can start from them and explained in the
notebook: `ltv` = loan / price; `affordability` = (5 % imputed interest on the loan + 1 %
of the price for maintenance + amortisation to two-thirds LTV over 15 years) / income, the
Swiss lending rule; `actual_burden` = interest_rate × loan / income.

Outcome: `trouble_36m` (1 if arrears of 90 days or more, or a forced restructuring, within
36 months of origination; base rate about 6 %).

Leaky: `reminders_sent` (payment reminders sent during the 36 months; strongly related to
the outcome and unknown at decision time). It exists so the decision-time rule has
something to bite on; the notebook drops it in the data-preparation step with the
explanation, and `applications_2026.csv` does not contain it.

Noise: `rooms`, `energy_label` and `years_client` carry no signal for trouble (rooms and
energy label do enter the price), so that LASSO has coefficients to zero out.

### Data-generating process

Prices: log price = canton level + elasticity × log area + property-type premium + age
effect (quadratic, renovation plateau) − distance decay + energy-label step + noise, such
that a linear model in levels reaches R² ≈ 0.75–0.8 on the test set and a log model does
better (the content of Exercise 1). Canton levels ordered ZH > (SG, AG, LU) > (BE, TG, SO)
at plausible CHF-per-m² magnitudes.

Trouble: log-odds = intercept + linear terms in `ltv`, `affordability`, `actual_burden`,
self-employment and age, plus three planted structures:

1. **Corner effect.** `affordability > 1/3` and `ltv > 0.80` together add a large jump
   (the two-threshold pattern of the SL3 Titanic slide: a tree finds it in two splits, the
   logit cannot represent it).
2. **Interaction.** `self_employed` × `saron` adds risk beyond the two main effects.
3. **Convexity.** The `actual_burden` effect is convex (quadratic above a knee), so that a
   +2 pp rate stress on SARON loans moves the tree ensembles' predictions more than the
   logit's (Exercise 7).

Calibration target, checked from the run before any prose is written: logit test AUC
about 0.78, gradient boosting and random forest about 0.84, tree of depth 3 in between.
The generator has a `--check` flag that fits a logit and a gradient booster on its own
output and prints the two AUCs, so the calibration is reproducible without the notebook.

### Sections

**0. The case.** The bank, the CRO's memo (three questions), the two data files with the
data dictionary summarised, "simulated, trouble rate inflated for teaching", how to work
as a team (roles rotate per part; everyone can explain every cell), the decision-time
rule stated once.

**Setup.** Imports, seeds, display options, data load, `head()`, shape, dtypes, missing
values, base rate.

**Part A — Recap.**

- *A1 Collateral valuation (linear regression).* Scatter of price against living area
  with the fitted line and the slope read as CHF per m²; multivariate model with canton
  and property-type dummies, `year_built`, `distance_center_km`; stratified train/test
  split by canton; RMSE against the predict-the-mean baseline; coefficient table read in
  CHF; residuals against fitted values (the fan that motivates the log model).
  **Exercise 1** log-price model, RMSE in CHF after back-transformation, one sentence on
  which to keep. **Exercise 2** `overpayment = purchase_price / predicted_value` on the
  full book, its distribution, and the trouble rate in the top decile vs the rest.
- *A2 Payment trouble (logistic regression).* Base rate and majority-class accuracy; the
  decision-time table (which columns the bank knows when it decides; `reminders_sent`
  dropped with the explanation); features standardised on the training set; logit;
  coefficients as odds ratios in business terms; predicted probabilities; confusion matrix
  at 0.5; precision/recall; ROC and AUC from probabilities against the baseline 0.5; the
  two errors with CHF costs (a bad loan approved: expected loss about CHF 60,000; a good
  loan rejected: lost margin about CHF 8,000), and why 0.5 is the wrong threshold. No
  undersampling (stated as a deliberate difference from unit 02: the probabilities stay
  calibrated for the cost-based threshold).
  **Exercise 3** threshold sweep from 0.02 to 0.5, expected cost per 1,000 applications,
  the cost-minimising threshold. **Exercise 4** trouble rate above vs below the 1/3
  affordability line and above vs below 80 % LTV, and the rate in the corner.

**Part B — Advanced methods (worked, intuition first).**

- *B1 LASSO.* The feature set widened with the noise columns and a few derived ones;
  `LogisticRegression(penalty="l1")` over a grid of C, the coefficient path plotted, the
  survivors named, `LogisticRegressionCV` picking C, AUC against the plain logit; one
  paragraph on ridge and elastic net.
- *B2 Decision tree.* Depth-3 tree on the decision-time features, plotted and read aloud
  as credit rules; a 2-D grid of the empirical trouble rate over (LTV, affordability) with
  the tree's splits drawn on it, showing the corner; depth sweep 1–12 with train and test
  AUC (overfitting); `min_samples_leaf` as the brake.
- *B3 Random forest.* Test AUC for 1, 5, 25, 100, 300 trees (the panel of interviewers);
  permutation importance on the test set; one sentence on why the forest cannot overfit
  the way the deep tree did.
- *B4 Gradient boosting.* A three-panel one-dimensional toy (trouble rate against
  affordability): the mean, then the first stump on the residuals, then after 20 rounds;
  `HistGradientBoostingClassifier` with early stopping on a validation split; XGBoost on
  the same split (`xgboost.XGBClassifier`, `early_stopping_rounds`); learning rate 0.03 /
  0.1 / 0.3 against rounds used and test AUC.
- *B5 SVM.* On the two features (LTV, affordability), standardised: linear kernel and
  RBF kernel boundaries plotted over the scatter, C = 0.1 / 1 / 10 for the RBF; then
  `SVC(kernel="rbf")` on all features with `decision_function` for the AUC; a note on
  why probabilities from an SVM need Platt scaling and why we report AUC from the
  decision function.
- *B6 Comparison.* One table: majority baseline, logit, LASSO logit, tree (depth 3), RF,
  GBM, XGBoost, SVM — test AUC, recall and precision at each model's cost-minimising
  threshold, expected cost per 1,000 applications, and an "explainable to a credit
  officer?" column. Reading the table as the CRO; the deploy-or-not discussion (model
  risk, explainability to the borrower and to the supervisor, monitoring).

**Part C — Exercises on the new methods.**

- **Exercise 5** tune RF (`max_depth`, `min_samples_leaf`) and GBM (`learning_rate`,
  `max_depth`) with 5-fold stratified cross-validation on the training set; table of CV
  AUC; test AUC of the winner reported once.
- **Exercise 6** score `applications_2026.csv` with the logit and the chosen model at each
  model's threshold; count the disagreements; for three of them, explain the disagreement
  with the depth-3 tree's rules.
- **Exercise 7** rate stress: +2 pp on SARON loans in the applications file, recompute
  `actual_burden`, re-predict with logit and GBM; expected trouble rate before and after
  under each model; which model reacts more and why (the convexity).
- **Exercise 8** five-bullet memo to the CRO: model, threshold, expected cost per 1,000,
  what to monitor after deployment, one caveat about simulated data.
- Reflection questions: does high LTV cause trouble (prediction vs. causality from SL1);
  what a real-data version would need; which column would you look for first as a
  leakage suspect in the bank's real systems.

### Conventions kept from the repo

Self-bootstrapping setup cell; data by raw GitHub URL; fixed seeds; every metric next to
its baseline; AUC from probabilities (or the SVM decision function); insight cells written
from a real run and saying "in this run"; outputs stripped; solutions beside starters, no
solution code in the student notebook; README badge and structure list updated; a licence
entry for the new data.

index or borrower data; grading rubric (the notebook is discussed, not graded).
